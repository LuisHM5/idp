# AGENTS.md

Guidance for AI coding agents working in this repository.

## Project Overview

**Documents Validator** is a document validation and extraction system on AWS: Amazon Bedrock (Claude) classifies and extracts fields, a Python Lambda applies deterministic validation rules defined in a JSON catalog (hot-reloadable via DynamoDB, no redeploy needed).

The engine is generic. Active catalogs are organized recursively under `catalogs/base/<domain>/` (portable official/typical contracts) and `catalogs/custom/<integration>/` (company/system-coupled output such as `PEDIMENTO_ERP`). As of 2026-09-08 there are 21 active types: nine established customs/fiscal/identity/insurance types, eight onboarding beta types (`CURP`, `ACTA_NACIMIENTO`, `COMPROBANTE_DOMICILIO`, `CONSTANCIA_NSS`, `PASAPORTE`, `CEDULA_PROFESIONAL`, `COMPROBANTE_ESTUDIOS`, `IDENTIFICACION`), three customs-expense CFDI XML beta types (`CFDI_GASTO_TERCERO_XML`, `CFDI_PAGO_DERECHOS_SANITARIOS_XML`, `FACTURA_LOGISTICA_XML`), and the ERP-coupled `PEDIMENTO_ERP_XML` beta mapping for a CFDI customs reference. The generic `IDENTIFICACION` type is explicitly declared (`segmentation_candidate: false`) and assesses document shape, never authenticity. Any directory named exactly **`save/`** is ignored recursively by build/sync. Do not describe parked JSONs as supported out of the box.

## Architecture

```
Upload API → S3 (raw/) → Step Functions (blueprint)
           → Bedrock Classification → Bedrock Extraction   [standard flow only]
           → Enrichment Lambda (handler.py) — branches on document type:
               ├── expediente pipeline (pipeline/) — customs, multi-document PDFs
               └── standard flow — single document, reuses Bedrock's extraction
           → EventBridge (APROBADO / RECHAZADO / REQUIERE_REVISION)
```

The Step Functions state machine itself comes from `@cdklabs/cdk-appmod-catalog-blueprints`; this repo supplies the enrichment, upload/query, and custom model-invoke Lambdas. See `documentacion/TRAZA_CODIGO_COMPLETA.md` for the full trace with file:line references.

`raw/{TYPE?}/{uuid}/file` is only where the object lives *during* processing — the blueprint (`QueuedS3Adapter`) moves it to `processed/{documentId}/{filename}` on any execution that completes without an exception (including a RECHAZADO validation outcome — that's a business result, not an infra failure) or to `failed/{documentId}/{filename}` only when the execution itself throws/times out. `documentId` is exactly the uuid the Upload API returned (see `patches/default-sqs-consumer-index.py` — no timestamp/filename appended), so `GET /documents/{id}` resolves it with a direct DynamoDB `GetItem` (`query-lambda/index.mjs::getById` tries that first, falling back to a `begins_with` Scan only when it misses). Deterministic per S3 key also means the Step Functions execution name is deterministic: a genuinely duplicate S3/SQS delivery of the same object either no-ops (Standard Step Functions' own `StartExecution` idempotency, while the original execution is still running) or raises `ExecutionAlreadyExists`, caught in the same patch and skipped rather than retried into the DLQ. Code/docs that need to read the original bytes after the fact must account for the raw→processed/failed move; see `documentacion/APIS_INTEGRACION.md` §1.1/§1.5/§2.3.

Key pieces:

- `bin/app.ts` — CDK entry point. Reads `-c env=dev|prod` (default dev), loads `.env.dev`/`.env.production`, instantiates the stack.
- `src/document-validation-stack.ts` — Main CDK stack. Wires Upload/Query Lambdas, the Bedrock pipeline, Enrichment Lambda, DynamoDB catalog, EventBridge broker, and prod-only hardening (API keys, WAFv2, custom domain).
- `src/prompt-generator.ts` / `src/document-catalog.ts` — Generate Bedrock classification/extraction prompts at synth time from the **legacy DSL only** (`extraction_fields`/`extraction_hints`). They do not understand the field-centric `fields` DSL — `pnpm preview-prompts` shows no extraction fields for a field-centric type even though extraction works fine (it happens Python-side, not through this prompt).
- `src/document-processing/resources/enrichment-lambda/` — Python 3.12 validation engine (do not modify `handler.py` lightly; extend via catalog config and validators instead).
  - `config/catalogs.json` — **Bundled catalog. GENERATED — do not edit, gitignored.** Produced by `pnpm build` (`scripts/sync-catalogs.mjs`) from active JSON files under `catalogs/**`.
  - `document_catalog.py` — Loads catalog entries (bundled JSON + DynamoDB overrides); detects which DSL a type uses by the presence of the `"fields"` key.
  - `validators/` — `engine.py` is the dynamic rule engine and the sole arbiter of which `rule_type`s exist (`_dispatch_rule`). `base.py`/`identification.py`/`fiscal.py`/`internal_formats.py` back the legacy/standard flow's `validator_module` mechanism. `validators/customs/*` are thin shims — customs rule *logic* lives in the catalog JSON and in `pipeline/expediente.py`.
  - `pipeline/` — the expediente pipeline: `pdf_pages.py` (pypdf layout text + parallel Textract OCR fallback per scanned page; `load_image_page` is the equivalent single-page entry point for a standalone JPG/JPEG/PNG — e.g. a photographed ID — Textract reads those bytes directly, no pypdf/PDF-wrapping involved, since a field-centric type like `INE` isn't necessarily backed by a PDF; `process_pdf`'s `source_format` param picks the right one, defaulting to the PDF path unchanged), `segmenter.py` (Bedrock page-range classification with deterministic markers, or — when the caller declared the type — no model call at all: a single segment, unless that type declares `page_selection.multi_instance`, in which case the file is split DETERMINISTICALLY into one segment per instance from the catalog's own `start_markers`/`page_of_pattern`/`duplicate_key_pattern`. That is what stops a PDF holding three foreign invoices from collapsing into one document with one invoice number; it costs nothing — pure regex over text Textract already produced — and is cheaper than not splitting, since each instance is extracted with its own 1-2 pages instead of the whole file. Detected by catalog SHAPE, never by TYPE_ID. Fail-open in every uncertain case: back to today's single whole-file segment. On the UNDECLARED path the model is told a reprint is its own document (correct — page text can't tell), and `_collapse_duplicate_segments` then applies the same identity to same-type segments, relabelling copies `OTRO`/`COPIA_DUPLICADA` rather than deleting them, so page coverage stays complete and both routes agree), `text_extractor.py` (catalog-schema extraction incl. nested/repeatable fields, chunked, parallel per-chunk), `expediente.py` (orchestrator: per-segment extraction — parallelized via `ThreadPoolExecutor`, `EXTRACT_WORKERS` env var — cross-document checks, tracking/provenance, and per-stage wall-clock in `tracking.timings` (pageLoad/segmentation/extraction/validation, ms) so "it took 56 seconds" can be broken down without re-running the document), `envelope.py` (assembles the v2 envelope both pipelines return — see "Output shape": the field-compaction rules, `classification_of`, and the `fit_to_budget` size guard all live here, deliberately out of `handler.py` and free of AWS so they're unit-testable on their own), `liquidacion.py` (fills `LIQUIDACION_NORMALIZADA` computed fields via concept-alias/source/filter mapping declared directly on catalog fields), `normalize.py` (deterministic amounts/dates/pedimento-number/UUID normalization + regex reference recovery), `qr_recovery.py` (corrects PATENTE/NUMERO_CONSECUTIVO/ANIO_PEDIMENTO/ADUANA_DESPACHO from the pedimento's embedded QR, gated by `QR_RECOVERY_ENABLED`; its `find_marker_page` is a thin wrapper over `page_selector.score_pages` — one scoring implementation, not two), `page_selector.py` (catalog-driven "which pages are worth paying for" — and, via `split_instances`, "where does each instance of this type start and end": scores each page by how many DISTINCT `page_selection.markers` its text matches, so `_extract_segment` sends only those pages to Bedrock instead of the whole segment — measured 86 pages -> 16 on a real expediente. **Opt-in per type** by declaring `page_selection` in the catalog, hot-reloadable via `pnpm sync:one`; `PAGE_SELECTION_ENABLED=false` only ever disables. Two cheap exits run BEFORE any scoring, both processing the document whole: `min_pages` (5) — a short document is one Bedrock chunk either way, so filtering saves tokens but not a call, while a bad marker could still drop a needed page — and `expected_pages` (a count or `[lo, hi]`), the size of ONE document of this type: an upload no bigger than that IS the document, not a bundle containing it. Neither counts as fail-open. A type whose length is genuinely unpredictable declares `expected_pages: "auto"` instead: no size shortcut, and when the markers DO fail open, `pipeline/page_locator.py` spends one cheap Bedrock call on the segmenter's own ~450-char page digests to locate the type's ranges rather than extracting every page's full text (~$0.012 vs ~$0.09 on a real 86-page expediente). It only ever runs after the free path gave up, it returns "don't know" (process everything) on any untrustworthy answer — including a range covering the whole document — and its cost is billed openly as its own `BedrockPageLocator` service, never folded into extraction. A type can also declare DOCUMENT BOUNDARIES — `start_markers`, `end_markers` and, most usefully, `page_of_pattern` whose two capture groups (current, total) let ANY page reveal its whole document's span. These apply only to pages already confirmed by `markers`, so a neighbouring CFDI's own "Página 1 de 6" can't open a span, and when declared they REPLACE `follow_pages`. Measured on real expedientes they fix two correctness bugs, not just cost: `follow_pages` was dragging in the unrelated DODA that followed the last pedimento page, and a pedimento's scanned cover page (no text, so score 0) was being dropped — it is now recovered from the next page's "Página 2 de 5". Fail-open itself is the invariant: no markers, nothing over `min_score`, or a selection wider than `max_ratio` all mean "process every page" — a selection is never TRIMMED to fit a number, since that drops real content exactly the way blind page truncation does. Calibrate with `pnpm paginas` before trusting a marker list. **Truncation and selection are mutually exclusive** (`expediente._page_cap_for`): a declared type whose selection is active is NOT blindly truncated by `MAX_PAGES`, because truncation runs first and would leave the selector choosing among only the first 50 pages of a 68-page upload — a pedimento on page 63 would be gone before it could be seen. Such a type gets the far higher `max_source_pages` (500) purely as a Lambda-exhaustion guard. Everything else — no `page_selection`, `enabled: false`, the kill-switch, and any upload with NO declared type (the applicable selector isn't known until the segmenter has read the pages) — keeps `MAX_PAGES` exactly as today. Each filtered document carries a `pageSelection.savings` block that keeps billed and estimated strictly apart: `billedInput/OutputTokens` are what Bedrock reported, while `estimated*` prices the expensive call that was never made — input from the tokens-per-character density of the call that DID run, output from avoided chunks (each chunk emits one full schema JSON, and output costs 5x input). Validated against a real counterfactual run to within 0.6% on cost. **Page saving ≠ token saving**: dropping 81% of a real expediente's pages cut 67% of its tokens, since the pages worth keeping are the text-dense ones — quote tokens for cost, pages for OCR volume), `xml_document.py` (deterministic `ElementTree`-based sibling to `expediente.py` for types whose fields declare `xpath` instead of `hint` — no Bedrock, no OCR; `handler.py` routes to it by the uploaded file's `.xml` extension, not by TYPE_ID; see `catalogs/README.md` → "Tipos con fuente XML"), `tabular_document.py` (same idea for `.xlsx`/`.xlsm`/`.csv`: fields declare `cell`/`column` instead of `hint`, extraction is a grid lookup via `openpyxl`/stdlib `csv` — see `catalogs/README.md` → "Tipos con fuente tabular"), `result_common.py` (tracking/provenance and error-result shape shared by `expediente.py`/`xml_document.py`/`tabular_document.py` so all three pipelines' results are interchangeable to `handler.py`), `bedrock.py` (shared Bedrock Converse helper — same-model retries, JSON parsing, usage tracking; also owns model resolution — `resolve_model`/`_model_candidates`, catalog `model_id`/`model_ids` vs. env config, see `catalogs/README.md` — and the model-unavailable fallback, `_invoke_with_fallback`/`_MODEL_UNAVAILABLE`, that switches to a different model entirely rather than retrying the one that failed — logs each switch, and `fallback_events()` reports expected-vs-actual model + retry count per stage, surfaced as `tracking.modelFallbacks`, present only for stages that actually switched), `model_fallback.py` (the ordered fallback-model list + switch budget `_invoke_with_fallback` consults — DynamoDB-hot-reloadable via `FALLBACK_MODELS_TABLE`/`FallbackModelsTable`, same import-not-create pattern as the catalog table; falls back to a hardcoded default order when the table is unset, empty, or unreachable, so this is never a hard DynamoDB dependency).
  - `extractors/` — Textract wrappers (`textract_analyze_id.py`, `textract_bedrock.py`) used by the standard flow's optional re-extraction fallback.
  - `indexing.py` — Promotes the final classification to indexed DynamoDB columns (`DocumentType`, `ProcessedAt`, `DocumentTypeName`, `ValidationStatus`, `ContainedDocumentTypes`, `DocumentName`, `Tracking`) so the query API filters by type without a Scan. `Tracking` (a Map) mirrors the envelope's top-level `tracking` object field-for-field in PascalCase (`_TRACKING_FIELD_MAP`: CreatedAt/UpdatedAt/ProcessingStartedAt/ProcessingCompletedAt/ProcessingSeconds/ProcessingTime/Timings/Schema/AppOrigin/ModelIds) — full parity, never a cut-down subset — on the item itself rather than only inside the `EnrichmentResult` JSON blob. Since v2 there is exactly one `tracking` in the envelope (it used to be duplicated verbatim inside `expediente`). Floats (`ProcessingSeconds`/`ProcessingTime`, the per-stage `Timings`, and any future float nested in `Schema`) go through `_decimalize()` recursively — boto3's resource API rejects a raw float anywhere in the structure. Best-effort: never fails validation. Backfill older items with `pnpm backfill:index`.
  - `unique_keys.py` — Writes one lookup row per **unique key** a type declares in its catalog schema (`unique_key` on a field, or at type level for legacy-DSL types), keyed `TIPODOC#<normalized value>` in the `UniqueKeyTable`. That's what turns `GET /documents?docType=X&field=Y&value=Z` into a single Query instead of a Query over every document of the type plus an in-Lambda match. Generic: detect by DSL shape, never by TYPE_ID — any type that declares one gets the fast path for free. The four normalizers (`upper`/`alnum`/`digits`/`raw`) are applied identically at write time here and at read time in `query-lambda/index.mjs::normalizeKeyValue`, so a caller can send `26 07 0823 6001630` or `260708236001630` and hit the same key — **if you change one, change the other** (`tests/unit/test_unique_keys.py` pins them together). Best-effort like `indexing.py`, and a miss is never a false negative: the query Lambda falls back to the per-type walk, so a document indexed before the key was declared is still found (slower). Backfill with `pnpm backfill:keys`.
  - `custom_validators/*.mjs` — Optional Node.js custom validators for logic beyond regex (standard flow only, see below).
- `src/document-processing/resources/upload-lambda/index.mjs` — Node.js 20 REST endpoint, **`POST /documents`** . The route was renamed from `/upload`, which stopped being true once the endpoint stopped receiving the file. `POST /upload` is still wired in `document-validation-stack.ts` as an undocumented alias so existing integrations keep working — it is deliberately absent from `openapi.yaml` and `API_USO.md`, which document `/documents` only. Removing it is two lines in the stack. **One flow only: `POST /documents` never carries the file.** It returns a presigned S3 `PUT` URL and the client uploads straight to S3, for every size. The old inline mode (`contentBase64`) was removed and now answers `400 INLINE_UPLOAD_REMOVED` — it made request SIZE pick the code path, and base64's ~33% inflation blew Lambda's hard 6MB sync-payload cap somewhere past ~4MB of real file. Do not reintroduce it. Accepts `application/json` **or** `application/x-www-form-urlencoded` (parsing lives in `body-parser.mjs`, a pure AWS-free module so it can be unit-tested — the SDK is runtime-provided and not installed locally; in a form body `metadata` is a JSON string). **The presigned `PUT` carries NO extra headers.** SigV4 presigning hoists `x-amz-*` headers into the query string, so the object metadata (`model-id`, `app-origin`) already travels inside `uploadUrl` and is covered by the signature — `X-Amz-SignedHeaders` is just `host`. Sending them as headers too makes S3 answer `403 AccessDenied: There were headers present in the request which were not signed`, a 403 that reads like a permissions problem and is not. Verified against the real bucket; do not reintroduce an `uploadHeaders` field telling callers to echo anything. Resolves the caller's `x-api-key` against the `AppsTable` DynamoDB table to a human-readable app name, carried as `app-origin` S3 object metadata (same channel as `model-id`) for traceability. The caller's own `metadata` rides the same channel, normalized by `body-parser.mjs`'s `normalizeMetadata` to what S3 can actually hold (lowercased keys, flat US-ASCII scalar values, 2KB total) and stripped of the two reserved keys above — so a body field can never impersonate another app. From there the SQS consumer patch reads it back off the object as `uploadMetadata`, `handler.py` puts it on the envelope as `metadata`, `indexing.py` promotes it to the `Metadata` column, and `GET /documents?meta.<clave>=` filters on it. Rejecting a bad value HERE matters: at the presigned `PUT` the same problem surfaces as an S3 `403 SignatureDoesNotMatch` that reads like a permissions bug.
- `src/document-processing/resources/query-lambda/index.mjs` — Node.js 20 REST read/search/metadata endpoints (`GET /documents/{id}`, `GET /documents/{id}/file`, `GET /documents?docType=...&system=...&meta.<clave>=...&field=...&value=...`, `PATCH /documents/{id}/metadata`). The four search filters are ANDed and only `docType` is evaluated in DynamoDB; the rest run in the Lambda over what it returned. `field`/`value` may be repeated (paired by position), which is why the handler reads `multiValueQueryStringParameters` and not just `queryStringParameters`. The query-string parsing and matching rules live in the AWS-free sibling `search-filters.mjs`; the flat ASCII/2KB merge-patch contract lives in `metadata-rules.mjs`, tested together with upload normalization. `PATCH` changes only the authoritative DynamoDB `Metadata` map plus version/audit columns, never validation status or the immutable S3 result; reads overlay that map. Enforces per-app document access (`AccessScope`/`AllowedDocTypes`/`AllowFieldSearch`/`AllowMetadataWrite` from AppsTable) — a denied single document is `404`, a denied capability is `403`. `GET /document-types` (paginated, 5/page) and `GET /document-types/{type}` are the catalog-discovery pair — `type`/`displayName`/`description` always, `schema` (the catalog's `fields` tree) only with `?includeSchema=1`, since a type like `PEDIMENTO_ADUANAL` has dozens of nested fields. Logic lives in the AWS-free sibling `document-type-catalog.mjs` (merge/scope/paginate — see its tests); `index.mjs` only does the DynamoDB Scan (deliberately uncached, unlike `knownTypesCache`, so a `pnpm sync:one` shows up immediately) and the bundled-JSON read. The bundled fallback is `document-types.json` (written by `scripts/sync-catalogs.mjs`, same file `knownTypes()` uses for `docType=` name resolution — extend `writeTypeIndex()` there, not `bundledTypes()` here, if the shape changes) with `description`/`fields` now included alongside the pre-existing `displayName`/`aliases`/`uniqueKeys`.
- `catalogs/` — **THE single source of truth for document types**. Type files are discovered recursively; any `save/` subtree and every `_*.json` file are ignored. See "Catalog DSL" below and `catalogs/README.md` for the full spec.
- `scripts/` — CLI tooling: catalog sync, prompt preview, local/e2e processing, comparisons, backfill, app/API-key registration (`manage-apps.mjs`). See the Commands table. `_report_lib.py` (no `pnpm` command of its own) holds the DynamoDB-reading/normalization/formatting/CSS shared by `reporte-costos.py`, `reporte-documentos.py`, and `reporte.py` — change a normalization rule there once, not three times.
- `src/document-processing/multi-model-document-processing.ts` — Subclass of the blueprint's `BedrockDocumentProcessing` that points the classification/extraction steps at our own Lambda (`resources/model-invoke-lambda/`, Bedrock **Converse** API) so any Bedrock model works, not just Anthropic. Uses the construct's documented `classificationStep()`/`processingStep()` extension points — **do not** move this back to patching `node_modules`. Its overrides run during `super()`, so their state lives in a module-level `WeakMap`, never in class fields (with `target: es2022`, field initializers run after `super()` and would wipe it).
- `patches/default-sqs-consumer-index.py` — Patch applied by `scripts/patch-construct.mjs` during `pnpm build`. Also reads the uploaded object's `app-origin` S3 metadata (best-effort `head_object`) and forwards it as `appOrigin` on the Step Functions input, so it reaches the enrichment Lambda's result envelope for every document, not just ones that trigger re-extraction.
- **`AppsTable`** (`document-validation-apps[-dev]`, DynamoDB, one per stack) — registry of per-app API keys/usage plans created via `pnpm apps:register` (not CDK-managed beyond the table itself; see `scripts/manage-apps.mjs` and `documentacion/AMBIENTES_Y_SEGURIDAD.md`). PK `ApiKeyId`. Read by the Upload Lambda, written only by the CLI script.
- **`CostTable`** (`document-validation-costs[-dev]`, DynamoDB, `RETAIN`) — per-document AWS cost audit trail, separate from the tracking table on purpose (finance/audit concern, not a document-query one). PK `DocumentId`. Written best-effort by `enrichment-lambda/cost_audit.py` (`handler()`, after `write_index_attributes`) with a $ breakdown per service — Bedrock segmentation/extraction/upstream classification+processing, Textract OCR, an approximate Lambda compute cost (`pipeline/pricing.py` has the rates — **every model in `model_fallback.DEFAULT_FALLBACK_MODELS` must have its own entry there, since that list switches models on its own; a model missing from the rate table is silently priced at the default model's rates, which is how every MiniMax run got reported at ~2x until 2026-09-04. `tests/unit/test_pricing_coverage.py` pins it**), plus a `PageSelection` attribute (present only when page selection actually filtered) carrying pages/chars/chunks/tokens saved and `estimatedCostAvoidedUsd` — deliberately OUTSIDE `Services`, since those are billed amounts and this prices a call nobody made; never add it into `TotalCostUsd`. Written through `_decimalize()` (it carries floats, which boto3 rejects at write time); surfaced by `pnpm costos` (per-document + roll-up), `pnpm reporte:costos` (md/html section, `SeleccionPaginas` xlsx sheet, `PageSel.*` columns) and `pnpm reporte` (filter-aware dashboard card, hidden when the current cut has none). `_report_lib.normalize_cost_item` casts it out of `Decimal` — DynamoDB returns every number as one and `reporte.py` embeds rows with `json.dumps`. See `documentacion/COSTOS.md` §7. Read by `pnpm costos` (`scripts/ver-costos.py`). Full detail: `documentacion/COSTOS.md` §7.
- **`UniqueKeyTable`** (`document-validation-keys[-dev]`, DynamoDB, `DESTROY`) — lookup from a business identifier to the document that carries it. PK `UniqueKey` (`TIPODOC#<normalized value>`), SK `DocumentId`, plus `DocumentType`/`FieldName`/`Value`/`NormalizedValue`/`ContainerType`/`ProcessedAt`/`ValidationStatus`/`DocumentName`/`IndexedAt`. Written best-effort by `enrichment-lambda/unique_keys.py` (`handler()`, after `write_index_attributes`), read by the query Lambda's fast path. A separate table rather than another attribute on the document item because an expediente is ONE item holding N documents, each with its own type and its own key — a GSI partition key can only carry one value per item. `DocumentId` is the SORT key, not part of the partition: the same identifier legitimately appears in more than one upload (a re-upload, a corrected expediente) and collapsing those onto one row would lose all but the last, so "unique" is a declaration of intent, never an enforced constraint. `ContainerType` goes through `index_type_of` like every other derived column, so a mixed bundle reports the container there rather than repeating the comma list — that column answers "loose, or inside a package?". `DESTROY` (unlike `CostTable`'s `RETAIN`): this is a derived index, not history — `pnpm backfill:keys` rebuilds it from the stored `EnrichmentResult`s. **`scripts/backfill-index.mjs` and `scripts/backfill-keys.mjs` are documented mirrors of `indexing.py`/`unique_keys.py` and carry their own `indexTypeOf`: a backfill that skipped it would write comma values straight into the GSI partition key.** See `catalogs/README.md` → "Unique keys".
- **`FallbackModelsTable`** (`document-validation-fallback-models`, DynamoDB, genuinely shared across dev/prod — unlike the catalog table, which is per-environment) — ordered list of Bedrock models to switch to when the requested one is unavailable (`pipeline/model_fallback.py`). PK `Rank` (N), attrs `ModelId` (S) + optional `Enabled` (BOOL). Imported not created (same reasoning as the catalog table), gated by `enableFallbackModels` (on by default in `bin/app.ts`); table missing/empty/unreachable → the pipeline just uses its hardcoded default order instead of failing. See `documentacion/GUIA_DESPLIEGUE_Y_USO.md` §5.6.

## Catalog DSL (field-centric v4)

`PEDIMENTO_ADUANAL.json` uses the current DSL: each field is declared **once**, as a key of a `fields` dict, carrying its type, whether it's required, its extraction hint, and its own `validation` — instead of being repeated across `extraction_fields`/`extraction_hints`/`required_fields`/`validation_rules` (the legacy DSL, still supported by the engine for types that use it, but no active type does today).

```jsonc
"NOMBRE_DEL_CAMPO": {
  "type": "string",              // string | number | boolean | date | object | array
  "required": true,
  "hint": "Dónde vive el dato en el documento, en español.",
  "validation": [ { "rule_type": "regex", "pattern": "...", "message": "..." } ],
  "fields": { /* only if type == "object": same shape, recursive */ },
  "item_fields": { "$common": [...], /* only if type == "array" of rows */ },
  "computed": true                 // only if the pipeline fills it, not the model
}
```

- The DSL a type uses is detected purely by the presence of the `"fields"` key in its raw JSON (`document_catalog.py`) — never hardcode logic to a specific `TYPE_ID`; detect by DSL shape so any future type gets the same support for free.
- A type with `"fields"` is routed to the expediente pipeline automatically (extraction requires it — the legacy prompt generator can't read `fields`), even without `pipeline: "expediente"`. See `catalogs/README.md` → "`pipeline: 'expediente'`: qué controla realmente" for the exact rules.
- **Auto-classification candidacy is `is_segmentation_candidate` (`document_catalog.py`), NOT `pipeline: "expediente"`.** It is decided by catalog SHAPE — the type has a `field_tree`, its fields are readable from page text (no `xpath`/`item_xpath`/`cell`/`column`, which is what keeps the `_XML` types out), and it has a `description` for the prompt to discriminate by. A type opts OUT with `"segmentation_candidate": false`; `PEDIMENTO_ERP` does, because it is the SAME physical document as `PEDIMENTO_ADUANAL` with ERP field names, so a text classifier has nothing to choose between them — you pick that rendering by declaring it. This used to be `is_customs_type`, which excluded field-centric types such as `PEDIMENTO_ADUANAL` from unlabelled classification. A type the CALLER declares explicitly is always a candidate, gate or no gate.
- Cross-document rules are **not** gated by `pipeline: "expediente"` either: `get_cross_document_rules()` returns every rule in `_shared.json`, and each rule declares the types it applies to in its own `documents: [...]` (`expediente.py::_docs_of`). So `is_customs_type` now has exactly one job — routing in `handler.py::_process`, where `type_entry.field_tree is not None` already covers every live type anyway.
- `validators/engine.py` is the only place that knows real `rule_type`s. An unrecognized `rule_type` doesn't error — it's silently recorded as `skipped: true, severity: "warning"`. Always check for `"skipped": true` in returned checks before assuming a new rule is miscalibrated.
- `"unique_key": true` (or `{"normalize": "alnum"|"digits"|"raw"}`) on a scalar field declares the value that identifies ONE document of that type, indexed as `TIPODOC#valor` so searching by it is a single Query — see `unique_keys.py` above and `catalogs/README.md` → "Unique keys". Also accepted at type level (`"unique_key": "CAMPO"` / a list), which is the only form available to legacy-DSL types.
- Full spec (every `rule_type`, the `LIQUIDACION_NORMALIZADA` computed-field convention, `$common` item fields, cross-document rules, gotchas): **`catalogs/README.md`**.

## Output shape

**Envelope v2 (`envelopeVersion: 2`) — one document = one element of `documents[]`, always** (`pipeline/envelope.py`). That array is present with one document or with twenty, in BOTH pipelines (expediente and standard flow), because a consumer can't know in advance how many a PDF holds: a shape that depended on the outcome would force two code paths in every client and silently read the wrong one the day a supplier staples a second invoice. That was literally the old bug — the root `extractedEntities` was the FIRST main document's tree presented as "the document", the per-document map repeated those same values as bare scalars in a different shape, and only the first document's array rows travelled at all. The envelope's root now mirrors the root of the full S3 result (`documents`/`crossDocumentChecks`/`pages`), so `result` and `fullResult` are the same shape, one deeper than the other. **There is exactly one place for each datum: `documents[i].fields`.**

Each resolved field — scalar, object, or array, at any nesting depth — resolves recursively:
- scalar → `{value, confidence, valid}` + `reason` only when `valid` is false + `source` only when it is NOT `MODEL_EXTRACTION`
- object → `{fields: {SUBCAMPO: {...recursive...}}}`
- array → `{items: [ {fields: {...recursive per row...}} ]}` — rows are never dropped, since `len(items)` is the "how many line items" signal

**A field is omitted only when it has no value AND `valid` is true** — i.e. "the document didn't carry it and nobody required it". A missing required field keeps its `valid: false` + `reason`; so does a value discarded for low confidence (`value: null` plus the reason explaining it). Nothing informative is lost, and the noise of `{"value": null, "confidence": 0.0, "valid": true, "reason": null, "source": "MODEL_EXTRACTION"}` — 20% of the response on a 66-field type — is gone.

`source` is `"MODEL_EXTRACTION"` (implicit, never emitted) or `"NORMALIZED"`/`"QR_RECOVERY"`/... for values computed or recovered post-extraction — distinct from a field's `hint`, which is catalog input describing where the value lives on the document for the prompt. The verbatim model output (`extractedValue`, never invented) and its deterministic derivation (`normalizedValue`) live in the S3 full result, which the envelope never overwrites.

`documentClassification` says WHAT THE FILE HOLDS: the document TYPE when every main document shares one (even if there are several), and otherwise **those types comma-separated in order of appearance** (`PEDIMENTO_ERP,FACTURA_FLETE_EXTRANJERO`). `OTRO` segments (including duplicate copies) stay in `documents[]` so page coverage remains auditable, but never enter the classification and don't count toward `documentCount`.

**The readable label and the search key are two different needs, and `envelope.index_type_of` is the seam between them.** `indexing.py` writes `DocumentType` (and `cost_audit.py` its own grouping key) from `index_type_of(classification)`, which collapses a comma list back to `EXPEDIENTE_ADUANAL_MULTIDOCUMENTO`. That is not redundancy: `DocumentType` is a GSI partition key and a DynamoDB Query matches it exactly, so a bundle indexed under `A,B` would be invisible to `?docType=A`, and `query-lambda`'s `expandContainers` cannot enumerate partitions without a Scan — which is precisely what the container + `ContainedDocumentTypes` pair exists to avoid. Searching for the inner types keeps working unchanged. Anything comparing a classification against `AllowedDocTypes` (`canSeeDocument`, `canSeePendingDocument`) must split on commas and require EVERY type to be granted.

The envelope is the Lambda's return value, so it travels through Step Functions (256KB state payload — the binding limit, tighter than DynamoDB's 400KB item). `envelope.fit_to_budget` keeps it under `ENVELOPE_BUDGET_BYTES` (180KB) by replacing the LARGEST arrays with `{count, omitted: "size"}` first — largest-first so a 3-concept invoice never loses its rows to a 400-partida pedimento — and announces every drop in `omitted`. Measured on real expedientes (20 documents, every row included) the envelope is ~34KB, so this is a guard, not the common path; the complete result is written to S3 BEFORE any trimming.

**Writing is v2-only; reading understands both.** Envelopes stored before v2 are never rewritten, so every reader over stored data goes through a shared normalizer — `query-lambda/envelope-shape.mjs` (used by the query Lambda, `backfill-keys.mjs`, `backfill-index.mjs`) and `scripts/_envelope_shape.py` (used by `ver-resultado.py`, `_report_lib.py`). `unique_keys.py` reads both too, since `pnpm backfill:keys` walks results of any age. Full request/response shapes: `documentacion/api-docs/API_USO.md`.

## Environments & API security

Two environments via CDK context (`bin/app.ts` reads `-c env=dev|prod`, **default dev**, loads `.env.dev`/`.env.production`):

- **dev** (default) → stack `DocumentValidationStack-Dev`, **open** API on the random execute-api URL. For testing. A bare `pnpm run deploy` targets dev.
- **prod** → stack `DocumentValidationStack`, hardened: **API keys** (`x-api-key`) required on every method, **WAFv2** (rate-based + AWS managed rules), and a **custom domain** (`idp.alsuper.com`) when `DOMAIN_NAME`+`CERT_ARN` are set. All prod hardening is gated on `environment === "prod"` in `src/document-validation-stack.ts` (`isProd`, `src/document-validation-stack.ts:96`).

Each environment is a fully isolated stack (own Lambdas, Step Functions, S3, DynamoDB tracking table, KMS, EventBus) with a `-dev` resource suffix for globally-unique names. The catalog table is per-environment too (`document-validation-catalog` in prod, `document-validation-catalog-dev` in dev — imported by name from `CATALOG_TABLE`, see `src/document-validation-stack.ts:174`), so a `pnpm sync` in dev can never reach prod and dev's Lambdas hold no IAM grant on the prod table. Missing/invalid key → native 403 from API Gateway **without invoking the Lambda** (no backend cost for 401/403/404). Cert is bring-your-own: import with `scripts/import-cert.mjs` (renew in place with `--renew --arn` — zero downtime, no redeploy). Full guide: **`documentacion/AMBIENTES_Y_SEGURIDAD.md`**.

## Catalog Loading Precedence

When the enrichment Lambda runs, it loads types in this order (last wins):

1. `config/catalogs.json` — the single bundled catalog (built recursively from active catalog JSONs), shipped with the Lambda code.
2. DynamoDB (`CATALOG_TABLE` env var — per environment: `document-validation-catalog` / `document-validation-catalog-dev`) — overrides bundled entries when `enableDynamoCatalog: true` (default in `bin/app.ts`). This is what `pnpm sync`/`sync:one` (dev) and `sync:prod`/`sync:one:prod` write to.

`forceReloadCatalog: true` (default) reloads on every invocation (small perf cost, immediate DynamoDB effect).

Routing to the expediente pipeline (`pipeline/expediente.py`) happens if **any** of: `pipeline == "expediente"`, the event declares `expediente: true` explicitly, or the type declares `fields` (field-centric DSL — see above). Auto-classification candidacy is a separate, shape-based decision (`is_segmentation_candidate`) and cross-document rules are per-rule in `_shared.json` — see the Catalog DSL section.

## Declared document types (`documentType`)

`POST /documents` accepts ONE type or SEVERAL comma-separated, which is the only difference between the three modes. They travel as **one segment of the S3 key** — `raw/{TYPE}/{uuid}/file`, `raw/{A,B}/{uuid}/file`, or `raw/{uuid}/file` when none was declared — because that key is already the single carrier of this signal, re-read independently by `patches/default-sqs-consumer-index.py` (`requestedDocumentType`), `model-invoke-lambda/index.py` (`extract_manual_classification`) and `enrichment-lambda/handler.py` (`_declared_types_from_key`).

| Declared | `classificationMode` | Segmenter behaviour |
|---|---|---|
| one | `manual` | No model call at all (`_declared_segments`) — the whole file is that type, or one segment per `multi_instance`. |
| several | `guided` | The model runs, but `_candidate_types(allowed)` offers ONLY those types with no gate applied. `OTRO` remains internal; the response contains only requested types. |
| none | `auto` | Candidates by shape (`is_segmentation_candidate`). |

Two things that are easy to get wrong here:

- **`_page_cap_for` takes the whole list and answers ANY, not all**: if even one declared type selects its own pages, the upload is not blindly truncated to `MAX_PAGES`, because truncation runs first and would drop a pedimento on page 63 before its selector could see it. Extraction cost stays bounded per segment; page loading and OCR are capped by `max_source_pages` instead.
- **`normalize_declared_types` exists because `str` satisfies `Sequence[str]`.** Passing a bare string into a `declared_types` slot would otherwise iterate its CHARACTERS. Use it rather than an inline comprehension.

**How many of each type (`TIPO:N`)** rides alongside: `documentType=PEDIMENTO_ERP:1,FACTURA_FLETE_EXTRANJERO:all`. A single type without a suffix defaults to 1; several types default to `all` for every unsuffixed type. Two things to keep straight:

- **The counts travel as S3 object metadata (`document-counts`), NOT in the key.** The key carries the TYPES because three components parse it (`handler._declared_types_from_key`, the SQS consumer patch, `model-invoke`); the counts are read by exactly one, so they go through the same channel as `model-id`, which `handler._fetch_document` already returns. `body-parser.mjs` reserves the key so a caller cannot forge it.
- **The segmenter's internal map stays complete, the closed response does not** — `_apply_type_limits` and `_collapse_duplicate_segments` relabel excess/copies as `OTRO`, then `expediente._only_requested_segments` removes every non-requested segment before extraction. Missing finite occurrences get one range-null review marker per deficit; `:all` gets one only when the type is absent. Markers do not count in `documentCount`, validation counts, classification, or `ContainedDocumentTypes`.

`.xml`/`.xlsx`/`.csv` accept exactly one type (rejected at the API *and* in `process_xml`/`process_tabular`, since `scripts/procesar-docs.py` reaches those directly): there is no classification step to choose between schemas.

## How To Extend

Pick the lowest-impact path that solves the request:

1. **New document type** → pick the template that matches the SOURCE, not the business document — the same invoice can need a different template depending on what actually arrives (a scanned/printed PDF vs. the native CFDI XML vs. an Excel export are three different sources for the same real-world document, and often three different catalog types):
   - **PDF/scan (a model has to read it)** → copy `catalogs/_TEMPLATE.json` into `catalogs/base/<domain>/<TYPE_ID>.json` or `catalogs/custom/<integration>/<TYPE_ID>.json`, then edit using the field-centric DSL with `hint` per field (see `catalogs/README.md`).
   - **Already-structured XML** (CFDI, VUCEM, any fixed-schema XML) → copy `catalogs/_TEMPLATE_XML.json` into the matching base/custom folder, edit with `xpath`/`namespaces`/`item_xpath` per field instead of `hint` (see `catalogs/README.md` → "Tipos con fuente XML", and `catalogs/base/fiscal/FACTURA_HONORARIOS_XML.json` for a real, verified example). Deterministic extraction via `pipeline/xml_document.py` — **zero Bedrock cost**, but `documentType` is mandatory at upload (no vision-based auto-classification for raw XML).
   - **Already-structured tabular data** (XLSX report, CSV export) → copy `catalogs/_TEMPLATE_TABULAR.json` into the matching base/custom folder, edit with `cell`/`column`/`column_letter`/`header_row` per field instead of `hint` (see `catalogs/README.md` → "Tipos con fuente tabular"). Deterministic extraction via `pipeline/tabular_document.py` — **zero Bedrock cost** for XLSX; for CSV specifically, `documentType` is not just recommended but required to stay zero-cost (see the gotcha in that doc section). Same file/type serves both `.xlsx` and `.csv` if the column layout matches.

   Any of the three: edit the copied template (delete the `__NOTAS__`/`__COMENTARIO_*__` keys — documentation only, the loader ignores them but they don't belong in a real type), then `pnpm sync:one -- --type <TYPE_ID>` (immediate, DynamoDB) or `pnpm run build && pnpm run deploy` (bundled baseline). Re-syncing a type overwrites its DynamoDB row entirely. A type parked in any `save/` subtree can be revived by moving it into `base/` or `custom/` — but review it against the current field-centric DSL first. Any `_*.json` file is excluded by filename prefix; all non-`save` directories are searched recursively. A full sync reports stale enabled DynamoDB rows; `--prune` marks those rows `enabled=false`.
2. **New/changed extraction field or hint** → edit `fields.<NOMBRE>.hint`/`type`/`required` in that type's file under `catalogs/`. Hints are free-form Spanish describing *where* on the document the field lives.
3. **New `rule_type`** → extend `validators/engine.py` (`_dispatch_rule` + a `_check_<name>` function). Applies to every type automatically, config-driven from then on.
4. **New cross-document rule** (compares sibling documents inside one expediente) → needs real code, not just JSON: add a `rule_type` to `_shared.json` → `cross_document_validation_rules` *and* its logic in `pipeline/expediente.py::_run_cross_document_rules`.
5. **External API calls, cross-field checks, check digits — standard flow only** → create a `custom_validators/<name>.mjs` exporting `async function validate(entityMap, context)`, reference it via `custom_validator` in the type's catalog entry. Does **not** run for field-centric/expediente types (`PEDIMENTO_ADUANAL` included) — for those, use `cross_field_validation` in the catalog, a cross-document rule, or extend `engine.py` directly.

Avoid editing `handler.py` for feature work. It is the engine; features live in the catalog (`catalogs/`) and validators.

## API Documentation (keep in sync automatically)

`documentacion/api-docs/API_USO.md` (narrative reference, Spanish, curl examples) and `documentacion/api-docs/openapi.yaml` (formal OpenAPI 3.1 contract, served locally via `pnpm docs:api` — Scalar by default, Swagger UI at `/swagger`) are **both** single sources of truth for how to call the app's REST API. Both live together in `documentacion/api-docs/` — the self-contained package meant to be shared with an outside integrator who has zero context on the rest of the repo (see `documentacion/api-docs/README.md`). **Whenever you change the API surface, update BOTH files in the same change — do not defer it, and do not update only one.** This applies when you:

- add, remove, or rename a route in `src/document-validation-stack.ts` (the `DocumentUploadApi` RestApi — `addResource`/`addMethod`);
- change a handler's request or response shape in `src/document-processing/resources/upload-lambda/` or `query-lambda/` (body fields, query params, status codes, response JSON);
- change auth, payload limits, or the base URL/stage.

For each such change: edit the matching section of `API_USO.md` (endpoint table + the per-endpoint request/response/examples, keep curl/`pnpm` examples runnable, match the existing Spanish tone) **and** the matching path/schema in `openapi.yaml` (path parameters, request/response schemas under `components/schemas`, status codes, examples) — both in `documentacion/api-docs/`. After editing the spec, sanity-check it renders: `pnpm docs:api` (or lint it, e.g. `npx @redocly/cli lint documentacion/api-docs/openapi.yaml`). Both files carry a maintenance header comment repeating this rule. If the change is user-facing (new endpoint, changed request/response shape), also check whether `documentacion/api-docs/ejemplos/curl.md` and `ejemplos/csharp.md` need a matching update, and `documentacion/api-docs/API_RESUMEN.md`/`documentacion/APIS_INTEGRACION.md` for their own cross-references.

**API Gateway gotcha:** adding a route via CDK does not always redeploy the `prod` stage — a new route can return `403 Missing Authentication Token` even after a successful `pnpm run deploy`. If so, force a stage redeploy: `aws apigateway create-deployment --rest-api-id <id> --stage-name prod --region us-east-1`.

## Conventions

- TypeScript strict-ish CDK code, 2-space indent, double quotes, semicolons (see `src/document-validation-stack.ts`).
- Python is type-hinted and docstring-heavy (see `handler.py`). Keep it that way.
- Document IDs, field names, and classification labels in catalog entries are UPPER_SNAKE_CASE and Spanish (`NUMERO_PEDIMENTO`, `RFC_IMPORTADOR_EXPORTADOR`, `PEDIMENTO_ADUANAL`).
- User-facing messages and docs in the existing codebase are Spanish; match that when editing existing files. New files may be English if the user asks.
- Canonical validation status values: `APROBADO`, `RECHAZADO`, `REQUIERE_REVISION` (top-level); expediente/document-level uses `APPROVED`/`REJECTED`/`PARTIALLY_APPROVED`/`REVIEW_REQUIRED`/`PROCESSING_ERROR`; field-level uses `VALIDATED`/`INVALID`/`LOW_CONFIDENCE`/`NOT_FOUND`/`NOT_APPLICABLE`/`REVIEW_REQUIRED`. Do not invent new ones.
- Do not commit `.env.dev`, `.env.production`, or anything under `cdk.out/`, `dist/`, `node_modules/`, `config/catalogs.json`.

## Safety Notes For Agents

- This stack touches AWS (Bedrock, Textract, Lambda, API Gateway, DynamoDB, EventBridge, S3, WAFv2, ACM). Treat `pnpm run deploy*`, `pnpm run destroy*`, and any `aws dynamodb`/`aws apigateway` write command against a real account as high-risk and confirm with the user before running.
- The DynamoDB catalog table has `RETAIN` semantics (imported via `fromTableName`, one per environment: `document-validation-catalog` / `document-validation-catalog-dev`). `pnpm run destroy` does not remove it; `pnpm run destroy:full` does — irreversible for types that only ever existed in DynamoDB, and it defaults to the **prod** table name, so pass `--table document-validation-catalog-dev` when the target is dev.
- `iam-policy.json` defines the broad Bedrock invoke permissions the pipeline needs. Do not narrow it without verifying inference-profile ARNs still resolve.
- Test documents under `test-docs/` and events under `test-events/` are for local testing only; keep any PII out of commits.
- Most AWS-touching test/CLI commands cost real money (Bedrock + Textract) — see the cost column in `documentacion/TESTS.md` and the measured figures in `documentacion/COSTOS.md` before running a full suite repeatedly.

## Validation Before Handing Off

After changes, at minimum:

1. `pnpm build` to ensure TypeScript and the patch script succeed.
2. If the catalog changed: `pnpm sync:one -- --type <TYPE_ID> --dry-run` to validate marshalling, and — only if it's a legacy-DSL type — `pnpm preview-prompts` to confirm prompts still render (field-centric types won't show anything meaningful there).
3. If Python code changed, run `pnpm test:unit` (free) and, when the change could affect extraction/validation of pedimentos, `pnpm test:unit` first then flag to the user that `pnpm test:pedimentos`/`pnpm comparar` cost real money and should be run deliberately.
4. Mention any deploy, `sync`, or DynamoDB steps the user still needs to execute.
